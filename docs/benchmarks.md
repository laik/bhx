| 项 | 值 |
|---|---|

## 本地决策模型 Laya

同一份模型，两种后端，同样 8 次请求取中位：

| 候选数 | 输入 token | torch / MPS (fp32) | ONNX / CPU (fp16) | 加速 |
|---:|---:|---:|---:|---:|
| 3 | 40 | **58 ms** | 344 ms | 5.9× |
| 10 | 110 | **117 ms** | 912 ms | 7.8× |
| 30 | 310 | **235 ms** | 2207 ms | 9.4× |
| 120 | 1210 | **252 ms** | 2287 ms | 9.1× |

启动与资源：

| 项 | torch / MPS | ONNX / CPU |
|---|---:|---:|
| 冷启动到可用 | 5.5 s（权重已缓存） | 5.6 s |
| 首次推理 | 427 ms | 包含在冷启动内 |
| 稳态 3 候选 | 58 ms | 344 ms |
| 常驻内存 | 1.69 GB（MPS） | ~0.8 GB（图）+ 进程 |

首次运行需下载 torch 权重，加载耗时约 119 s（含下载），之后从缓存加载 4.4–5.5 s。

### 精度一致性

同一输入下 torch/MPS fp32 与 ONNX fp16 的输出几乎相同（测试 3 组，概率差 ≤ 0.001，选择一致）：

| 用例 | torch/MPS | ONNX/CPU |
|---|---|---|
| 导航目标 | e1 0.919 | e1 0.919 |
| 完成判定 | yes 0.866 | yes 0.866 |
| 表单提交 | e2 0.658 | e2 0.659 |

所以换后端不是「用精度换速度」，至少在这个规模上没有可观测差异。

### 发现

1. **瓶颈是 fp16 图在 CPU 上没有原生 kernel，不是算法本身。** 同一个 421M 参数模型换到 MPS
   跑 fp32，快了 6–9 倍。之前 0.5–4 s 的直觉全部来自 ONNX CPU 这一条路径。
2. **冷启动不再是差别。** 两个后端都在 5.5 s 左右，sidecar 常驻依然必要，但不再是选型理由。
3. **CoreML 执行提供器在这里没有价值。** ORT 报告图中 1957 个节点只有 124 个被 CoreML 支持，
   切成 62 个分区后大量拷贝，实测反而更慢（30 候选 3.3 s vs CPU 2.6 s）。
   而且 laya 在 macOS 上根本不尝试 CoreML（`onnx_agent.py:212` 只判断 CUDA）。
4. **int8 动态量化这条路暂时走不通。** `quantize_dynamic` 在 shape inference 阶段失败：
   `Inferred shape and existing shape differ in dimension 0: (1028) vs (256)`（外部数据 + 动态维度）。
   既然 MPS 已经把延迟压到 60–250 ms，这件事不再值得追。
5. **30 个候选之后延迟进入平台期，但准确性塌陷。** 30 / 60 / 90 / 120 个候选耗时接近，
   但顶层概率降到 0.16–0.24，概率 >1% 的候选只剩约 20 个。
   不是「算得动更多」，是「算得糊」。**候选多不等于信息多。**
6. **内存是新的代价。** MPS 常驻 1.69 GB，ONNX 约 0.8 GB。单 sidecar 无压力，
   但意味着不能给每个任务起一个 sidecar。

### 对设计的约束

- **默认后端改为 torch/MPS**，ONNX 保留为无 MPS 环境的回退。见 `sidecars/laya/decide.py`。
- Laya 只用于**低频、离散**决策：升级点定位、失败重定位、结果判定。
- **调用前必须先用规则把候选压到 ≤10 个。** 这不是性能优化，是正确性要求：
  多发候选不会更慢，但会更不准。
- 即使 58 ms，也**不进 30 Hz 的控制回路**。实时路径仍然靠策略循环，模型只负责低频改策略。
- Sidecar 进程单例、常驻，不按任务启动（1.69 GB / 5.5 s 起步）。

## CDP 基线（Phase 0 spike，2026-10-28）

自建薄 CDP 客户端（`spike/`，约 350 行），headless Chrome，1280×800 @2x，
本机 WebSocket，release 构建。三次运行结果一致，下表取其一。

| 操作 | n | p50 | p95 | 备注 |
|---|---:|---:|---:|---|
| `Runtime.evaluate`（CDP 往返） | 100 | 0.1 ms | 0.4 ms | 含 JS 执行 |
| `Accessibility.getFullAXTree`（小页面） | 30 | 0.5 ms | 2.1 ms | 12 KB, ~40 节点 |
| 元素索引构建（AX → 交互元素） | 20 | 0.4 ms | 0.8 ms | 5 个元素 |
| `DOM.getBoxModel` | 50 | 0.1 ms | 0.2 ms | backendNodeId → 盒模型 |
| `Input.dispatchMouseEvent`（mouseMoved） | 50 | **16.6 ms** | 17.1 ms | 单发一次移动事件 |
| 点击（move + press + release） | 50 | **16.6 ms** | 18.5 ms | 3 次调用 |
| 点击（press + release） | 50 | **0.4 ms** | 1.3 ms | 省掉 mouseMoved |
| 键盘按下+抬起 | 50 | **0.3 ms** | 0.6 ms | 持续按键的最小单元 |
| `Page.captureScreenshot`（JPEG q70） | 30 | **49.9 ms** | 62.8 ms | ~38 KB/张 |
| `Page.captureScreenshot`（PNG） | 10 | 49.8 ms | 85.2 ms | ~36 KB/张 |
| 端到端点击（索引→盒模型→点击→验证） | 20 | 16.7 ms | 17.2 ms | 20 次全部生效 |
| `Accessibility.getFullAXTree`（1000 行表格） | 10 | 103.0 ms | 106.7 ms | **4901 KB, 13422 节点** |

### 发现

1. **CDP 本身不是瓶颈。** 往返 0.1–0.5 ms，`Runtime.evaluate` 和 `DOM.getBoxModel` 便宜到可以随便调。
   自建客户端这条路线成立，不需要 `chromiumoxide` 也不需要 Playwright。
2. **`mouseMoved` 吃掉一次点击 97% 的成本。** 单发一次移动事件 16.6 ms，而 press+release 只要 0.4 ms。
   16.6 ms 接近 60 Hz 的一帧，几乎可以确定是输入管线在等帧对齐。
   这意味着：**默认点击绝不能先发 mouseMoved**，否则每次点击白白丢掉一帧。
3. **键盘只要 0.3 ms。** 30 Hz 循环的预算 33 ms，键盘操作完全撑得住。
4. **截图 50 ms，是视觉路径的硬成本。** 这个页面上 JPEG 与 PNG 大小相当（38 KB vs 36 KB），
   但复杂页面 JPEG 会明显占优；默认 JPEG q70 是对的。50 ms 也意味着视觉路径不可能进高频回路。
5. **大页面的 AX 树会爆炸。** 1000 行表格 → 13422 个节点、4.9 MB、103 ms。
   这是整个设计里最容易低估的点：不设预算、不做差分的观察层会在真实后台页面上直接失效。
   默认 `max_elements = 120` 不是保守，是必需。
6. **元素索引构建很便宜（0.4 ms）。** 可以在每次动作后重建，不必缓存。
   真正贵的是把 AX 树变成 JSON 传出来，不是筛选。

### 对设计的直接影响

- **`click` = press + release at target center，不发 mouseMoved。** `hover` 是独立动作。
  若某元素必须悬停才可点（hover-gated），由可执行性检查发现，再补发移动事件——
  这是例外，不是默认。
- `Input.*` 的调用次数比想象中重要：3 次调用 16.6 ms，2 次 0.4 ms，差的不是网络而是浏览器内部调度。
- 视觉路径的预算按「每步 50 ms + 模型时间」算，不要按「实时」算。
- Phase 0 退出条件达成：端到端单动作 p95 **17.2 ms** < 50 ms。

## Phase 1 端到端（2026-10-28）

`testkit/sites/admin`（登录 → 筛选 → 导出 CSV），`bhx` debug 构建，
Chrome 每次任务新起，headless。测的是**完整链路**，不是单条 CDP 调用。

| 场景 | 结果 | 说明 |
|---|---|---|
| 完整任务，连续 3 次 | 202 / 271 / 218 ms | 3 步 7 个动作 + 1 次下载，0 次模型调用 |
| 导出瞬间注入 `alert()` | 733 ms 完成 | 自动 dismiss 后继续，多出的是一次 500 ms 显式等待 |
| 取消（等待中的条件） | **85 ms** | 轮询上限 100 ms；取消后会话仍可用 |
| Chrome 启动 + 首次导航 | 0.9–1.8 s | 一次性成本，每个 session 付一次 |

MCP 路径（同一页面，同一进程复用）：

| 操作 | 中位 | p95 |
|---|---:|---:|
| `browser_navigate`（复用会话） | 12 ms | 16 ms |
| `browser_observe`（6 个元素） | **3 ms** | 6 ms |
| `browser_execute_actions`（1 次点击，含定位与滚动校正） | **9 ms** | 12 ms |

结论：

1. **小页面上观察比点击还便宜。** 3 ms 意味着「每次动作前重新观察」是可以承受的策略，
   不需要为省一次观察去做缓存失效的推理。这个结论只在小页面上成立，
   1000 行表格仍是 103 ms + 4.9 MB，预算与差分照旧是必需的。
2. **`scroll_into_view` + 重读盒模型让点击多花约 0.5 ms，值得。**
   Phase 0 的 0.4 ms 是「知道坐标且元素已在视口内」的理想值；
   9 ms 才是「从定位器开始」的真实成本。
3. **取消的延迟由轮询间隔决定，不由 CDP 决定。** 上限设在 100 ms，实测 85 ms。
   想压到 20 ms 就得把等待间隔降到 10 ms，那是 10 倍的 JS 往返，不划算。

## Phase 2 端到端（2026-10-28）

`testkit/run-phase2.sh`，`bhx task run`（debug 构建），headless Chrome 每个任务新起。
下表的 `elapsed_ms` 从**引擎开始启动浏览器**计时，到任务结束为止，所以包含 Chrome 启动
与恢复导航（约 0.6 s，见 R1 的拆分）。模型调用 0 次。

下表是最近一次 14/14 运行（`fail_when` 落地后）的任务耗时，括号里是多次运行观察到的范围：

| 用例 | 内容 | 任务耗时 | 说明 |
|---|---|---:|---|
| A1 | 登录 → 提取订单行为 JSON 产物 | **881 ms**（775–2252） | 2 步 5 个动作；冷启动后的第一次会明显偏高 |
| A2 | 3 页向导 → 服务端 422 校验 → 提交 | **750 ms**（704–875） | 6 步 10 个动作，跨 3 次导航 |
| A3 | 登录 → 筛选 → 导出 CSV | **815 ms**（660–1127） | 3 步 7 个动作 + 1 次下载 |
| A4 | 跨站点 6 步：提取 + 表单提交 | **905 ms**（904–997） | 15 个动作，2 个站点 |
| A5 | 弹窗确认 + 首次接口 500 → 重试 | **1283 ms**（1283–1351） | 失败尝试被 `fail_when` 提前终止；加它之前是 9008–9388 ms |
| R1 | `kill -9` 后的 resume（只重跑 s4） | **3719 ms**（3634–3801） | 含 3 s 的页面握手等待，见下 |

同一用例的波动来自三处：Chrome 启动、页面的 `fetch` 首次请求、成功条件的轮询相位
（25→100 ms）。任务越短，这几项占比越大，所以 A1 在冷启动后第一次跑会偏高。
要压掉这部分波动，得把「启动浏览器」与「任务执行」分开计时，Phase 3 加视觉路径时一并改。

R1 的 3.6–3.8 s 几乎全是 s4 本身：崩溃点被选在 `?slow=1` 的 3 s 审计握手期间，
恢复后必须重新等完这段。这正好说明恢复的是**状态**，不是「跳过等待」。

### 失败尝试的成本：9.4 s → 1.3 s

A5 最初的 9.4 s 里有 8 s 是失败尝试等满 `step.timeout_ms`，而真正的失败在几百毫秒内
就发生了——导出接口返回了 500，页面的 `#list-error` 已经可见。

现在步骤可以声明 `fail_when`，执行器在等待成功条件时同时轮询它。两个实现细节是必须的：

1. **动作前为真的失败条件要先清空再重算。** 否则第二次尝试一开始就看见上一次留下的
   错误横幅，立刻放弃——重试形同虚设。
2. **下载成功条件要改成轮询守卫（`try_wait`），不能阻塞在事件流上。** 阻塞等待时
   执行器没有机会看失败条件。`DownloadGuard` 因此保留已完成的路径，重复轮询结果一致。

实测：同一用例、同样的注入（1 次 confirm + 1 次 500），9.4 s → **1.3 s**，仍然 14/14。

### 恢复路径的额外开销

| 阶段 | 观测 |
|---|---|
| 崩溃后的第一次 `task resume`（判定中断、登记审批、返回 3） | 在打开浏览器之前返回，只做本地 SQLite 判定 |
| 批准后的 `task resume` | 3.6–3.8 s 总计，其中 s4 自身约 3.05 s（页面握手的 3 s 等待），其余约 0.6 s 是启动浏览器与恢复导航 |

结论：恢复的**逻辑**成本可以忽略，代价全在「重开一个浏览器」。这也是按任务保留
持久 profile 的原因——登录态与筛选条件还在，恢复后不需要从第一步重来。

## Phase 3 C 组：交互控制器（2026-10-28）

`testkit/run-phase3.sh`，debug 构建，headless Chrome，每任务新起。表中的
`controller.elapsed_ms` 是循环本身的时长（不含浏览器启动）。

| 用例 | 内容 | 循环耗时 | 动作数 | 结果 |
|---|---|---:|---:|---|
| C1 | 按住右键直到 x ≥ 120 | 367 ms | 1 | goal_met，退出后按键为空 |
| C2 | 画布坐标点击 | 102 ms | 1 | goal_met，落点 (80, 88) |
| C3 | 先右后下：观察状态切换按键 | 632 ms | 3 | goal_met，终点 (131, 109) |
| C4 | 不可能达成的目标，1.5 s 超时 | 1521 ms | 1 | deadline，x 到 344 后释放按键 |

三次运行结果一致（C4 的 1521 ms 是 1500 ms deadline + 一次 tick）。

结论：

1. **规则求值不贵。** 10 Hz 采样 + 30 Hz 求值在这个页面上只占循环时间的一小部分，
   剩余全是等 tick 和输入分发。
2. **超时的误差是一个 tick。** 1521 ms 对 1500 ms 的 deadline，说明没有补偿性突发。
3. **释放是退出的一部分，不是另一条路径。** 四个用例（含失败的那个）退出后
   `keys` 都为空，说明「先释放再关浏览器」这件事没有只写在成功分支里。

## Phase 3 B 组：视觉路径（2026-10-28）

`testkit/run-phase3.sh`，debug 构建，headless Chrome 每任务新起，
`testkit/vlm.py` 跑在 localhost:8790。表中的任务耗时从**引擎启动浏览器**计时，
所以包含约 0.5–0.7 s 的 Chrome 启动与 1 次截图（约 50 ms）。

| 用例 | 内容 | 任务耗时 | 模型调用 | 命中误差 |
|---|---|---:|---:|---:|
| B1 | 有语义 DOM 按钮，目标仍写 `{"visual": …}` | 609 ms | 1 | < 1 px（未逐点打印） |
| B2 | 无语义 canvas 按钮 | 650 ms | 1 | 0.67 px |
| B3 | 拖拽：两个视觉目标 + press/move/release | 881 ms | 2 | 起点/落点各 0.57 px |
| B4 | 按钮外观不变，等服务端确认 | 975 ms | 1 | 0.67 px（确认等待 300 ms+） |
| B5 | 换布局后同一描述重新定位 | 554 ms | 1 | 0.70 px |
| B6 | DOM 定位失败 → `fallback_visual` 改道 | 616 ms | 1 | 0.67 px |

另一次运行的耗时范围：B1 535–609、B2 624–650、B3 881–996、B4 975–1094、
B5 554–643、B6 549–616 ms。两次都是 41/41。

结论：

1. **视觉路径的单次成本 ≈ Chrome 启动 + 50 ms 截图 + 模型往返 + 动作与验证。**
   去掉约 0.6 s 的启动，一个视觉步骤在本地替身上是 200–400 ms；拖拽因为要定位两次，
   多一次截图与模型调用。
2. **误差来自颜色区域的包围盒，不是坐标换算。** 0.57–0.70 px 的偏差与 2× DPR 下
   一个物理像素（0.5 CSS px）同量级，说明 `bbox_norm → CSS` 与截图的尺寸校验没有引入偏移。
   换成真实 VLM 后误差由模型决定，这个数字不再可比。
3. **模型调用数与动作数一一对应。** 每次视觉定位恰扣 1 次预算；B6 先走 DOM 失败
   再改道，仍然只有 1 次调用——失败路径没有重复计费。
4. **这个表不衡量模型质量。** `vlm.py` 只按颜色选区域，延迟是本地 HTTP + 纯 Python
   PNG 解码，不是真实 VLM 的推理时间。要看模型侧数字，换 `BH_VLM_URL` 重跑同一套件。

## Phase 4 REST / WebSocket（2026-10-28）

`bhx serve`（debug 构建）与 testkit server 同机，任务用 `admin/task.json`（登录 → 筛选 →
导出 CSV），curl 计时，单次运行：

| 操作 | 耗时 | 说明 |
|---|---:|---|
| `POST /v1/tasks` → 202 | **10 ms** | 只做校验、登记与派发，不等浏览器 |
| `GET /v1/tasks/{id}` | **1.2 ms** | 任务行 + 步骤 + 审批 + 产物索引 |
| `GET /v1/tasks/{id}/events` | **1.3 ms** | 12 条事件，单次 SQLite 查询 |
| `GET /v1/tasks/{id}/artifacts/{name}` | **1.0 ms** | 108 B CSV，含路径校验 |

结论：

1. **HTTP 层不是成本。** 四个端点都在 10 ms 以内，任务耗时仍由 Chrome 启动和页面
   自身决定（同一任务 CLI 路径约 0.8 s）。REST 入口没有把浏览器生命周期做得更重。
2. **202 的价值是把「受理」与「完成」分开。** 客户端拿到 id 就能断开；结果从存储读，
   不依赖持有连接。
3. **事件读取与状态读取同价**（约 1 ms），所以轮询事件也不荒谬；WS 只是省掉了
   客户端自己的轮询，不是省服务端的读。

## Phase 4 Laya sidecar：延迟与零样本准确率（2026-10-28）

真实 Laya（`sidecars/laya/decide.py`，torch/MPS，加载 4.4 s），真实 testkit 后台页，
走 MCP `browser_verify`（每次工具调用新建 router，验证 sidecar 复用）：

| 场景 | 端到端 | 推理 | 判定 | 置信度 | 是否正确 |
|---|---:|---:|---|---:|---|
| 未登录页，目标「已登录并看到订单列表」 | 7.2 s（含浏览器启动 + 模型加载） | 656 ms | `achieved` | 0.67 | **否** |
| 登录后，同一目标 | 0.2 s | 60 ms | `not_achieved` | 0.54 | **否**（< 0.6 → `uncertain`） |
| 登录后，目标「导出产生了 CSV」 | 0.1 s | 59 ms | `not_achieved` | 0.75 | 是 |

同一进程的第二次调用不再付模型加载：`bhx mcp` 里两次 `browser_verify` 只 spawn 一个
sidecar 进程，60 ms 一次判定。

结论：

1. **契约与生命周期是通的。** 握手、常驻、跨 router 复用、推理超时后 kill 并重启、
   父进程退出时 sidecar 随 stdin EOF 退出，都有测试覆盖（`testkit/laya-smoke.py` 71 项）。
2. **零样本准确率不够用。** 在中文后台页上，登录前判「已完成」、登录后判「未完成」——
   两个关键判定都反了。装的是英文 checkpoint，Skill 也标注中文未测。因此默认顺序是
   **远程模型优先、Laya 兜底**；`BH_LAYA_PRIORITY=first` 才会把它放到前面。
3. **置信度不可当概率读。** 加载时即警告 temperature 被 clamp；0.54 / 0.67 只能用于排序。
   判定仍按调用方阈值三态处理，不因为「模型说了 achieved」就跳过 `uncertain`。
4. **延迟不是问题，准确率才是。** 60 ms 一次判定足够进任务回路，但在这个页面上
   省下的是一次远程调用，换来的是错误答案。要用它，先在自己的站点上测阈值与准确率。

## 歧义定位仲裁：Laya 做候选选择（2026-10-29）

`policy.arbitrate_ambiguous` 打开后，模型只在**已解析出的候选**里选一个。真实 Laya
（`sidecars/laya/decide.py`，torch/MPS）在 testkit 两个页面上的实测：

| 场景 | 候选 | 选择 | 置信度 | 是否正确 |
|---|---|---|---:|---|
| `/arbiter/export/`，目标「导出为 CSV」 | `导出 CSV` vs `导出 PDF` | **PDF** | 0.625 | **否** |
| 同上，`min_confidence=0.7` | 同上 | 放弃 | — | 是（拦住了一次错选，任务未派发任何点击） |
| 三候选（含无关的 `重置筛选`） | CSV / PDF / 重置筛选 | **CSV** | 0.779 | 是（无关项排最后，0.093） |
| `/arbiter/`，两个按钮**同名** `导出` | 交换提供顺序各一次 | 始终同一元素 | 0.672 / 0.831 | 不可判——它读的是 id，不是页面 |

延迟：单次判定 419–495 ms（三候选 419 ms，两候选 360–440 ms），端到端步骤
7.1 s（含 4.4 s 模型加载，同进程第二次起不含）。

结论：

1. **它能读标签。** 三候选里把无关按钮排到最后（0.093），说明输入里的描述真的被用上了；
   这正是 P0 那根线的意义——候选由解析器给出、描述由观察器生成，模型只做选择。
2. **同名候选它答得自信，但答案是任意的。** 0.83 比任何合理阈值都高，阈值拦不住。
   所以仲裁在**描述完全相同**时直接放弃，一次调用都不花：这是测出来的，不是假设的。
3. **阈值默认 0.7 有实测依据。** 真实错选的置信度是 0.625，正好落在 0.7 之下；
   这不是把阈值调去迁就某个模型，而是这类「猜错就操作错元素」的决策本就该比
   「判错结论」更保守（`semantic_verify` 用 0.6）。
4. **它仍不该排在远程模型前面。** 中文后台的两项判定在上一节里都是反的；
   默认顺序不变（远程优先、Laya 兜底），`BH_LAYA_PRIORITY=first` 才提前。

对照实验（评审第五节要的 A/B/C/D）现在只缺 C/D 两组的数据面：A（现有模型调用）
与 D（纯规则）本来就是验收标准里的默认路径（`model_calls` 恒为 0），B 就是这一节。
缺的是**同一批任务上**横向跑一遍的统一指标，见 `docs/roadmap.md`。

## 控制器里的模型选策略（2026-10-29）

`controller.decide`：模型每 `every_ms` 选一次策略，规则以 30 Hz 执行。验证页
`testkit/sites/plane/` 的两条航线故意不对称——左线 80 px/s（3.8 s 到火力线、5.2 s 内全部飞走），
右线 25 px/s（9 s 的时钟内根本到不了）。因此"先守哪条"的收益是离散的：3 分或 0 分。
分数取自服务端遥测 `/plane/__state`（页面每 250 ms POST），不取控制器自述。

| 模型答案 | 命中的规则 | 结果 |
|---|---|---|
| `left`（慢线，来得及） | `go-left` / `hold-left` | **得分 3**，两编队全灭；x 走到 110–175 |
| `right`（快线，来不及） | `go-right` / `hold-right` | **得分 0**，左线两架飞走；x 走到 295–340 |

两次运行**只有模型的答案不同**（`options` 顺序 + 替身模式），规则、随机性、时钟都一样——
这就是"模型做的决定真的改变了结果"的可复现形式。

真实 Laya（torch/MPS）在同一场景跑了三次：**三次都是 0 分**。

| 观察 | 数字 |
|---|---|
| 决策次数 | 2 / 4 / 4 |
| 命中的规则 | 每次都先 `go-left/hold-left`，**中途改成 `go-right`** |
| 结果 | 左线三架全部飞走（`alive L/R = 0/3`） |

它一开始选对了。问题出在**中途反悔**：左线飞机在 2.95 s 才进入火力带，而它在窗口打开之前
就切到右线，于是整个窗口空着。

把那一局真实的中盘状态单独喂给它（状态里明确写着 `nearest: "left"`、`leftAlive: 2`）：

| 选项顺序 | 答案 | 置信度 |
|---|---|---|
| left, right | **left** | 0.690 |
| right, left（对调） | left | **0.511** |

两个结论：

1. **它会用状态里的事实。** `nearest: "left"` 让它选了 left——这与前面"同名候选"的探针
   形成对照：那里页面没有可区分的信息，这里有。
2. **但它对事实的使用不稳。** 同一个状态、同一个正确答案，只换选项顺序，置信度从 0.690
   掉到 0.511——刚好压在 `min_confidence=0.5` 上面。也就是说这条阈值挡不住它反悔：
   错误的答案会以刚刚够格的置信度被采纳。

对设计的含义（比"能不能用 Laya"更重要）：**策略切换需要迟滞**，不是更高的阈值。
一次切换应当要求明显更高的置信度，或要求连续两轮一致，否则模型每抖一次，正在执行的
策略就被打断——这一局输的就是这个，不是它选错第一次。

延迟：单次判定 145–500 ms（两候选），端到端一次 9 s 的交互式任务总耗时 6–10 s
（含 4.4 s 模型加载，同进程复用后不再有）。`every_ms=1000` 时 9 s 内问 9 次，
`max_model_calls` 必须按这个数量级配。

## Phase 4 规划 Plan（2026-10-28）

同机、debug 构建、`testkit/planner.py` 替身（本地 HTTP，无推理）。计时包住整个 CLI
进程，所以包含 Chrome 启动、观察、一次模型往返；`plan --run` 还包含第二次浏览器启动
与任务执行（登录 → 筛选 → 导出）。

| 场景 | 耗时 | 模型调用 |
|---|---:|---:|
| `bhx plan --out` 第一次（Chrome 冷启动） | 1795 ms | 1 |
| `bhx plan --out` 第二次 | 417 ms | 1 |
| `bhx plan --out` 第三次 | 364 ms | 1 |
| `bhx plan --run`（含执行） | 1298 ms | 1 |
| `bhx plan --run`（含执行，第二次） | 1062 ms | 1 |

结论：

1. **规划一次 ≈ 一次观察 + 一次模型往返。** 冷启动后 364–417 ms 与 Phase 3 的
   单个视觉步骤同量级；多出来的部分是文本更长、状态序列化更贵，不是路由开销。
2. **规划与执行是两次独立的浏览器启动。** `plan --run` 的 1.0–1.3 s 基本等于
   `plan` 的 0.4 s + 任务执行的 0.6–0.9 s，没有复用浏览器；这是有意的取舍——
   规划用的浏览器在写 spec 后就丢弃，执行由引擎掌握生命周期和下载目录。
3. **这个数字不含模型推理。** 替身立刻返回固定步骤；真实 LLM 的端到端时延由模型和
   网络决定，套件只保证 harness 侧不额外放大（一次调用、无重试、无重复观察）。

## Phase 5 延迟预算（2026-10-28）

控制器是本地固定频率循环，不调模型；下面的数字测的是「一次 tick 花多少、抖动多大」，
不是模型时延。测量来自 `interactive.stopped` 事件里的 `evals` 与 tick 间隔分位数
（`tick_ms_p50/p95/max`），取自本机实测，不是推算。

| 场景 | tick 目标 | ticks | evals | p50 | p95 | max |
|---|---:|---:|---:|---:|---:|---:|
| 30 Hz，1 条规则 + 目标（`interactive-smoke.py` A 段） | 33 ms | 17 | 18 | 33 ms | 35 ms | 35 ms |
| 60 Hz，5 条规则 + 目标（站内 3 s deadline） | 16 ms | 188 | 188 | 15 ms | 17 ms | 31 ms |
| 30 Hz 持续 30 s（soak，一直按住方向键） | 33 ms | 909 | 909 | 33 ms | 34 ms | 42 ms |

结论：

1. **谓词求值从「每规则一次往返」降到「每 tick 一次」。** 60 Hz、5 条规则时，
   旧实现每 tick 要做 6 次 `Runtime.evaluate`（目标 + 5 条规则），3 s 约 1100 次；
   现在 188 次，与规则条数无关。`evals == ticks` 就是这条断言的现场证据。
2. **抖动在 2 ms 量级，慢 tick 来自采样而非规则。** 30 s soak 里 p50 33 ms、p95 34 ms；
   60 Hz 的 max 31 ms 来自首次采样（含一次 JS 往返），之后被锚点配速拉回。
   配速按锚点计算、落后不补发，所以一次慢 tick 不会引起一阵爆发。
   30 s 里 909 个 tick（29.3 Hz，含浏览器启动的首个慢 tick），服务器进程平均 CPU
   3.0–3.6%，结束时页面确认按键已释放。
3. **模型只能在 tick 边界介入，频率上限就是一个 tick。** 控制器循环里没有任何模型调用；
   `interactive_update_policy` 投递到 watch 通道，下一个 tick 采纳（16–33 ms），
   中间版本被丢弃、只留最新。这就是「模型可介入频率」的实测上界：不是每帧，
   是每 tick 一次，且旧策略不会覆盖新策略。
4. **采样率与动作率本来就分开。** `observe.max_hz`（默认 10 Hz）决定 JS 采样，
   `tick_hz`（默认 30 Hz）决定规则/动作；60 Hz 循环里 samples 仍是 27/188 tick 的密度。

没有采到的数字：真实页面上的规则复杂度对 tick 的影响。测试站点是轻量 JS，
上面的 p95 是 harness 侧开销的下界；页面自己阻塞主线程时，`Runtime.evaluate` 会等它。

## Phase 6 定时执行（2026-10-28）

`schedule-smoke.py`（`run-phase4.sh` 第十组，61 项断言）在空 home 里把 admin 任务的
密码改成 `${cred:password}`，`schedule add --every 1s` 后先不带值跑一次（必须拒绝），
再带 `BH_CRED_PASSWORD` 跑一次，然后验证禁用/启用/删除与常驻模式，最后用两个到期调度测并发上限。下面是本机一次
实测（单次，随机器与冷热不同）：

| 指标 | 实测 |
|---|---:|
| `schedule add` 后的首次运行 | 立即（不等一个间隔） |
| 任务耗时（`bhx stats` 的 `duration`） | 1470 ms |
| `schedule run --once` 墙钟（进程启动 + 浏览器 + 任务 + 退出） | 1.50 s |
| 动作 / 失败动作 | 7 / 0 |
| 模型调用 | 0 |

| 常驻模式（无 `--once`） | 启动即跑到期项，跑完继续轮询；1h 间隔在 0.6 s 内不重跑 |
| 无效间隔（`5 minutes` / `500ms` / `30`） | 拒绝，并说明单位或 1 s 下限 |
| 两个到期调度，`run --once`（默认并发） | 1.99 / 2.40 / 2.05 / 2.42 s（四次），同一时刻最多 1 个 `running` |
| 两个到期调度，`run --once --concurrency 2` | 1.59 / 1.63 / 1.78 / 1.53 s（四次），观察到两个同时 `running` |
| 1 s 间隔 + 常驻模式（运行约 2 s） | 首次到期即打印 `skipped_overlap`，进程继续；禁用后本次运行仍记为 `succeeded` |

结论：

1. **槽位先消费再运行。** 失败后立刻再跑一次得到 `no schedule due`，说明失败不会变成
   重启后的自动盲重试；这条用行为验证，不是靠读代码。
2. **凭据名字入库、值只从环境读。** 缺值时根本不启动浏览器（站点下载数不变），
   运行成功后任务 home 里也搜不到明文。
3. **首次立即生效。** `add` 与 `run --once` 之间不需要 `sleep`；测试里唯一的等待是
   第二个间隔（1 s）。
4. **并发节省的是浏览器启动与等待的重叠。** 两个约 1.5 s 的任务，并行比串行快
   0.4–0.8 s（约 20–32%）；任务本身包含固定轮询等待，所以加速比低于 2。默认仍是 1，
   因为并发消耗的是本机浏览器实例与站点配额，不该由库替用户默认打开。

## Phase 6 远端浏览器（attach，2026-10-28）

`remote-smoke.py`（`run-phase4.sh` 第十一组，17 项断言）自己起一个 headless Chrome
（临时 profile、`--remote-debugging-port`），`bhx` 只通过 `BH_CDP_URL` 连上去，
从不走本地启动路径。本机一次实测：

| 指标 | 实测 |
|---|---:|
| `BH_CDP_URL=http://127.0.0.1:<port>` 跑完 admin 工作流（任务墙钟） | 602 ms |
| 同上，`ws://…/devtools/browser/<id>` 形式 | 356 ms |
| 同一任务的本地启动路径（前一次定时执行实测，含冷启动 Chrome） | 1470 ms |
| `bhx` 退出后远端 Chrome | 仍在运行 |
| 运行前后页面 target 数 | 1 → 1（自己开的标签已关） |
| 坏端点（空闲端口） | 5.1 s 失败；错误含 `CDP` 与 `--remote-debugging-port` |
| 坏端点那次运行记录的状态 | `failed`（`phase=launch`），无 `pending` |
| 坏端点那次运行的站点下载 | 0 |

结论：

1. **省掉的是浏览器启动，不是任务。** 会话级的 3 步工作流本身仍是几百毫秒；
   attach 与本地启动的差别主要在「谁来起 Chrome」，1470 ms → 602 ms 就是这个差。
   两次测量的机器状态不同，这组数字只表示量级，不是恒定值。
2. **清理要按 target，不按数量。** Chrome 的扩展 `background_page` / `service_worker`
   会自己出现和消失；第一版断言用 target 总数比较，失败在「多了一个 service_worker」
   而不是「标签没关」。现在只数 `type == "page"` 且按 id 关闭。
3. **坏端点必须快速、可见地失败。** 5.1 s 来自 5 s 的端解析超时；失败会写进任务状态，
   `stats` 里看不到 `pending`——否则一个打错的端口会留下永远等人的任务。

## Phase 6 trace 回放器（2026-10-28）

`bhx trace <id> --out DIR` 现在除 `trace.json` 与 `artifacts/` 外还写 `trace.html`：
一个自包含页面（无 CDN、无构建、`file://` 可开），按真实事件间隔回放。
`trace-stats-smoke.py` 用真实 Chrome `--dump-dom` 打开它，确认脚本
真的把时间线渲染了出来。本机一次实测（19 条事件的 admin 任务）：

| 指标 | 实测 |
|---|---:|
| `trace.html` 大小 | 20 KB（其中数据 4.4 KB） |
| `trace.json`（pretty） | 7.2 KB |
| 页面源码里的外部引用（`src=` / `href=` 指向 http） | 0 |
| `--dump-dom` 渲染出的事件行 | 19 行（18 条 `class="ev"` + 1 条选中的 `class="ev sel"`） |
| 步骤卡 / 产物链接 | 3 张 / 1 条，链接指向包内真实文件 |

结论：

1. **自包含是有代价的，但很便宜。** 模板（CSS + 原生 JS）约 16 KB，gzip 前比一张截图
   还小；换来的是「把目录发给别人就能看」。
2. **验证渲染，而不是验证文件存在。** 只断言 `trace.html` 存在会漏掉脚本语法错误
   （真实发生过：`const start` 与 `function start` 重名，页面一片空白）；`--dump-dom`
   里出现脚本生成的 `class="ev"` 才算通过。
3. **失败优先。** 有失败动作时页面打开就选中它；成功任务则停在最后一个事件。

## Phase 6 步骤截图（2026-10-28）

`policy.trace_screenshots` 打开后每个步骤写一张 JPEG（quality 70）；失败步骤无论如何
都写一张。`trace-stats-smoke.py`（45 项断言）跑出的本机实测：

| 指标 | 实测 |
|---|---:|
| 每步截图耗时（事件间隔，含写盘与入库） | 43 / 65 / 43 ms |
| 每张大小 | 35 KB / 23 KB / 23 KB（1280×800，admin 页） |
| 3 步任务的截图总量 | 81 KB |
| 未开开关的成功任务 | 0 张 |
| 未开开关的失败任务 | 1 张，名字指向失败的那一步 |
| 回放器 DOM 里的 `<img>` | 6 个（3 张步骤卡 + 3 条时间线），全部指向包内文件 |

结论：

1. **默认只截失败是划算的。** 成功运行零额外成本；失败运行多一张 20–35 KB 的图和一个
   CDP 往返，换来的是失败现场。
2. **全序列的成本可以接受但要显式开。** 每步 ~50 ms 和几十 KB；长任务（几十步）
   会把这个数字放大，所以要由 policy 决定而不是默认打开。
3. **截图走产物表。** 它和下载文件同一套 name/bytes/sha256，`task artifacts`、
   `trace --out`、播放器直链都不用另写代码——新增的只有一条事件和一个 kind。

## Phase 6 语义校验截图（2026-10-28）

`policy.semantic_verify.include_screenshot` 打开后，任务在观察之后截一张视口 PNG
随校验请求发出，同一份字节留在任务目录。`semantic-smoke.py`（58 项断言）与
`laya-smoke.py`（80 项断言）的本机实测：

| 指标 | 实测 |
|---|---:|
| 截图尺寸 / 大小 | 1280×800 / 30,984 B（admin 页，PNG） |
| 请求体增量 | `data:image/png;base64,…`，约 41 KB |
| 任务耗时（暖机后各 3 次） | 不开：683 / 702 ms；开启：643 / 691 ms |
| 替身收到的字节数与 sha256 | 与任务摘要、`artifacts/verify-final.png` 三者一致 |
| 事件顺序 | `task.verify.screenshot` 在 `task.verified` 之前 |
| 只配 Laya 且开启截图 | 任务 `failed`（`laya has no vision`）；sidecar spawn=0、decide=0；预算仍扣 1 次尝试 |
| 未开启 | 请求无 image、无事件、无文件 |
| `trace --out` 回放 | 包内 `*-verify-final.png`；真实 Chrome 渲染后 `<img src="artifacts/…verify-final.png">` 存在 |

结论：

1. **本地没有可测出的延迟。** 截图的成本是 ~41 KB 的 base64 请求体和一个 CDP 往返，
   任务总耗时与不开的样本区间重叠（643–702 ms）；对远程视觉模型，上传时间才是大头。
2. **审计靠同一份字节。** 存盘的不是「之后再截一张」，而是发给模型的那份
   `Vec<u8>`，sha256 三方相同；回放与追责都指向同一个文件。
3. **没有视觉的后端必须失败，不能退化成文字判定。** Laya 明确拒绝图片，且根本不启动
   sidecar；这次尝试仍按「按尝试计」扣预算，但不会产生一个假装看过图的 verdict。
